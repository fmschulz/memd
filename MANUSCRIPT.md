# memd: A Local MCP Server for Shared Agent Memory, Task-Oriented Knowledge Artifacts, and Hybrid Retrieval

## Abstract
`memd` is a local software system for giving one or more agents access to persistent shared memory through the Model Context Protocol (MCP). The software addresses two distinct knowledge-management problems. The first is storage and retrieval of ordinary memory chunks such as code, notes, traces, and documentation fragments. The second is storage and retrieval of structured task history, including goals, motivation, hypotheses, tool choices, parameters, evidence, failure modes, validation, uncertainty, and follow-up actions. The repository implements these capabilities in a single Rust workspace that exposes an MCP server, a local CLI, persistent and in-memory storage backends, hybrid dense and sparse retrieval, structural code search, debugging-oriented trace retrieval, and benchmark harnesses for offline retrieval and task-memory evaluation.

The design of `memd` is explicitly local-first. Persistent operation writes into a user-controlled data directory rather than a remote service. Retrieval combines Candle-based dense embeddings with HNSW approximate nearest-neighbor search and Tantivy BM25 sparse search, then applies hybrid reranking. A feature-gated ONNX cross-encoder reranker is available as an optional retrieval refinement stage, but it is not the default embedding path. The checked-in benchmark artifacts indicate that the structured `task.*` lifecycle materially improves recovery of task rationale and evidence relative to generic chunk search on the repository’s hardened Phase 5 corpus. Taken together, these design choices make `memd` a software substrate for long-running, multi-agent technical work in which later agents must recover not only raw text but also the reasoning and evidence behind previous actions.

## Introduction
Agent memory systems often fail for predictable reasons. Raw chunks can be stored, but later retrieval frequently loses the distinction between intent, evidence, execution details, and conclusions. A code fragment, an experiment note, and a final decision may all be represented as undifferentiated text, which makes it difficult for later agents to determine what was tried, what failed, why a method was chosen, and what evidence supports the current state of the work. `memd` addresses this problem by separating flexible memory chunks from a structured task-artifact lifecycle while retaining a common retrieval substrate.

The repository presents `memd` not as a single retrieval algorithm but as an end-to-end local software system. It includes storage, indexing, retrieval, schema projection, MCP tool definitions, structural analysis, maintenance infrastructure, and evaluation harnesses. The present manuscript describes that software as implemented in the checked-in repository state rather than as a speculative roadmap. Claims are therefore limited to behavior visible in code, configuration, and benchmark artifacts that are present in the repository.

## System Overview
At the highest level, `memd` exposes 30 MCP tools grouped into five functional surfaces: generic memory operations, task-oriented knowledge artifact operations, context retrieval, structural code analysis, and debug/trace inspection. The generic memory surface supports chunk addition, batch addition, search, retrieval, deletion, feedback, statistics, metrics, and maintenance-oriented operations. The task surface supports starting a task, recording progress, delimiting tool runs, adding evidence, finishing tasks, retrieving full task histories, and filtered task search. The context, structural, and debug surfaces extend the system beyond raw memory retrieval into codebase understanding and operational tracing.

The primary user-facing execution mode is now a shared local MCP daemon over HTTP. In this mode, `memd` is launched once on a machine and multiple agent clients such as Codex and Claude-style MCP integrations connect to the same `/mcp` endpoint. The original stdio subprocess mode remains available as a legacy transport for client-launched server instances. A CLI mode is also provided for direct local interaction, debugging, export, and initialization of guardrail files and client configuration. The configuration system intentionally remains small: it covers data directory, log level, log format, MCP transport, and the HTTP bind/path settings, with defaults favoring local persistence in `~/.memd/data`, structured JSON logging, and localhost binding.

## Core Design Decisions
The most important design decision in `memd` is the separation between raw memory chunks and structured task artifacts. The `memory.*` interface is intentionally flexible and appropriate for code snippets, documentation fragments, ad hoc notes, and broad context indexing. The `task.*` interface is intentionally structured and records the shape of substantive work. The codebase and checked-in schema documentation make clear that this structured layer is not simply a richer note format. It is a canonical artifact envelope designed to preserve the information later agents usually need but generic chunk search loses: the goal of the work, why it matters, what was attempted, what tool and parameters were used, what evidence was obtained, and what remains uncertain.

The second major design decision is to keep canonical task artifacts separate from retrieval projections. Canonical envelopes are stored as task artifacts and normalized side-table records, while retrieval chunks are derived from those artifacts and optimized for search. This avoids conflating the source of truth with the text that happens to be most retrievable. It also permits `task.search` to apply exact filters on task metadata before performing query-aware reranking over a narrower candidate set.

The third major design decision is to avoid dependence on a single retrieval paradigm. `memd` combines dense retrieval and sparse retrieval rather than assuming that one supersedes the other. Candle-based embeddings and HNSW indexing support semantic similarity, while Tantivy BM25 and code-aware tokenization preserve exact lexical matching for identifiers, error strings, paths, and code-adjacent text. Hybrid retrieval then uses reciprocal-rank fusion and reranking, which is a pragmatic response to the fact that agent memory contains both ordinary language and code-like strings.

The fourth major design decision is local durability without a heavyweight external database. `memd` stores payloads in append-only segment files, protects writes with a WAL, and keeps lightweight metadata in SQLite. This design offers clear crash-recovery boundaries and avoids storing full payloads twice. It also permits a directory structure that is inspectable and portable by ordinary filesystem tools.

## Storage and Data Model
Persistent `memd` deployments write into a data directory containing `metadata.db`, tenant-specific segment directories, WAL files, dense warm-index state, and sparse lexical-index state. Payload bodies are stored in append-only segment files under each tenant, while SQLite holds lightweight metadata such as chunk identifiers, tenant and project affiliation, chunk type, segment location, timestamps, and index lifecycle state. This division keeps metadata queries efficient without turning SQLite into the payload store.

Write-time behavior is designed to preserve both durability and searchability. New chunks are first serialized into WAL records, then appended to the active segment, then entered into metadata tables, and finally scheduled or executed for indexing. Long texts are split at add time into sub-chunks and annotated with chunk-position metadata so that retrieval can operate on smaller units without losing reconstruction hints. This split logic is shared across storage backends to keep behavior aligned between in-memory testing and persistent operation.

The task-memory layer adds a second data model. Canonical task artifacts are typed as `task_start`, `task_progress`, `run_start`, `run_finish`, `evidence`, and `task_finish`. These artifacts can carry project, agent, and session identifiers, goal and motivation statements, hypotheses, scientific or technical questions, chosen tools and versions, commands, parameters, inputs, outputs, metrics, evidence summaries, validation notes, uncertainty, and follow-up actions. The repository further documents normalized tables such as `task_artifacts`, `tasks`, `task_events`, `runs`, `evidence`, `datasets`, `entities`, and corresponding join tables. This schema design is central to the software rather than an auxiliary feature.

## Retrieval Architecture
Dense retrieval in `memd` is implemented with a Candle-based embedder. The dense search coordinator constructs a `CandleEmbedder`, derives the embedding dimensionality from the loaded model, embeds chunk text during indexing, and embeds the query at search time. Embeddings are stored in an HNSW warm index built with `hnsw_rs` and cosine distance. The repository defaults are tuned for a modest local memory footprint rather than maximal global scale, which matches the system’s local-first design.

Sparse retrieval is implemented with Tantivy BM25. Indexed text is tokenized with a code-aware tokenizer, which is important because agent memory and codebase artifacts often contain mixed prose, identifiers, and filesystem paths. Sparse results are generated per tenant, and hybrid retrieval fuses dense and sparse candidate lists with reciprocal-rank fusion.

Full reranking occurs after candidate retrieval. The default `hybrid-feature` path uses a feature-based reranker that combines fused score, recency, project affinity, and chunk-type preferences. The optional `hybrid-cross-encoder` path adds an ONNX cross-encoder that scores query-document pairs directly. The repository now documents this accurately: ONNX is not used for the default embedding path, and it does not participate in write-time indexing. It is used only as an optional reranking stage at query time. If the cross-encoder feature is not compiled in or the scorer cannot initialize, the software falls back to feature reranking rather than failing closed.

The retrieval architecture also includes a tiered path with semantic cache, hot tier, and warm tier fallback. In this design, dense query embedding occurs first, then cached or promoted results may be returned before the system falls back to the ordinary warm-tier hybrid search path. This tiered structure is intended to accelerate repeated or locality-heavy access patterns without changing the underlying storage model.

## Structural and Debug Retrieval
`memd` is not limited to free-text memory search. The repository includes a structural subsystem based on tree-sitter parsers and associated query services. This subsystem can index symbols, call edges, imports, and other code structure across multiple languages. A query router then classifies user intent and directs lookups to structural or semantic backends as appropriate, with fallback to semantic search when structural results are absent or incomplete.

The debugging subsystem extends the same local memory substrate to tool traces and stack traces. The repository includes trace parsing, error signature normalization, and query services for tool calls and errors. These capabilities matter because long-running agent work often spans code indexing, execution traces, and diagnostic context rather than static documents alone.

## How to Use memd
The fastest path to using `memd` is to build the binary and start the shared local daemon:

```bash
cargo build --release
./target/release/memd --mode mcp --transport http --http-bind 127.0.0.1:8787
```

For disposable testing, a fully in-memory HTTP daemon can be started with:

```bash
./target/release/memd --mode mcp --transport http --http-bind 127.0.0.1:8787 --in-memory --data-dir /tmp/memd-demo
```

Current client configuration follows the same daemon model. Codex CLI is configured against `~/.codex/config.toml`, Claude Code is configured against `~/.claude.json`, and the repository now includes helper scripts that register both clients against the shared local endpoint and verify that Codex and Claude can read each other’s writes through `memd`.

In practice, agents should use the software in two different ways. Raw searchable context should be added with `memory.add` or `memory.add_batch`, and broader retrieval should use `memory.search`. Substantive work should be recorded through the `task.*` lifecycle: `task.start` before work begins, `task.progress` for meaningful changes in understanding, `task.run_start` and `task.run_finish` for concrete runs, `task.add_evidence` when results support or weaken a claim, and `task.finish` when a meaningful stopping point is reached. The checked-in task schema documentation and skill files are explicit that agents should search first, avoid repeating known failed approaches without a reason, and use a consistent tenant identifier when they are meant to share memory.

The CLI provides an additional operational surface. It supports addition, search, retrieval, deletion, statistics, export, and initialization of guardrail and MCP configuration files. The bundled skill package under `memd-skill/` is therefore not separate from the software’s design; it is part of how the repository operationalizes correct agent behavior on top of the core server.

The optional ONNX reranker is enabled only when needed. To build and run that path, the user must compile the `cross-encoder-reranker` feature and launch `memd` with `--search-variant hybrid-cross-encoder`. The repository now includes a real ignored smoke test that calls the ONNX scorer directly. That test is useful because ordinary unit tests in the reranker layer may use lexical fallback in test configurations.

## Evaluation Artifacts
The repository contains two benchmark families. The first is an offline retrieval benchmark over BEIR-style datasets and a small smoke dataset. These artifacts are designed for ordinary retrieval benchmarking and support deterministic confidence intervals through seed and bootstrap controls. The second is a task-memory benchmark that is more specific to the software’s core thesis: that structured task artifacts recover information generic chunk search loses.

The checked-in Phase 5 report shows a large separation between those two modes on the hardened corpus. The flattened generic chunk baseline failed to recover the correct task within the top three results and achieved `MRR = 0.00`, whereas the structured task-memory mode achieved `hit@3 = 0.96` and `MRR = 0.82`. The same report notes that task-memory seeding is slower because more retrieval projections are written, but the resulting search is both more accurate and faster on the benchmark corpus. These numbers are repository artifacts rather than fresh reruns performed for this manuscript, so they should be read as documentation of the current checked-in software state rather than as an exhaustive external evaluation.

## Limitations
Several limitations are visible in the repository and should be documented plainly. First, the software is still local-first rather than a hosted memory service. The new HTTP daemon enables one-machine shared sessions and can be exposed across machines by an operator over a private network or tunnel, but the repository does not yet implement built-in multi-user authentication or server-enforced per-account isolation. `tenant_id` remains a caller-supplied logical partitioning key rather than a security boundary. Second, the checked-in task schema documentation states that a formal external schema specification and migration history are not yet provided. Third, parts of the compaction subsystem are implemented as infrastructure with some lifecycle behavior still evolving. Fourth, the ONNX cross-encoder is optional and feature-gated, and automatic runtime download is documented only for supported Linux targets. Finally, while the repository includes benchmark harnesses and checked-in results, not every possible retrieval configuration has committed benchmark outputs.

Another practical limitation is that in-memory mode does not represent the full persistent architecture. It is useful for smoke testing and local experimentation, but it does not exercise Candle-backed persistent indexing, segment files, SQLite metadata, or the full hybrid retrieval path. Users evaluating `memd` for long-lived agent memory should therefore prefer persistent mode and the checked-in benchmark harnesses when possible.

## Conclusion
`memd` is best understood as a local knowledge substrate for agent systems rather than as a thin wrapper around vector search. Its main contribution is the integration of durable storage, hybrid retrieval, and a task-oriented knowledge artifact model that preserves the rationale and evidence behind previous work. The software’s architecture makes explicit tradeoffs: locality over managed service complexity, hybrid retrieval over single-mode retrieval, structured task artifacts over undifferentiated notes, and conservative fallbacks over fragile optional dependencies. The repository’s checked-in benchmark artifacts support the central claim that this structure matters in practice, at least on the provided hardened task-memory corpus.

For users, the practical message is straightforward. Use `memory.*` for raw searchable context. Use `task.*` for substantive work that later agents must actually understand. Run persistent mode for real deployments. Enable the ONNX reranker only when the additional dependency surface is justified. Read the benchmark artifacts as implementation evidence, not as a universal performance guarantee. Within those boundaries, `memd` provides a coherent and well-instrumented local platform for shared agent memory.
